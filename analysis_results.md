# Forensic Engine Audit: ppos-preflight-engine

## Overview
This audit investigates why a ~19.6 MB PDF resulted in a `COMPLETED` job status but an empty/missing analysis state in the UI. We examined the core analysis pipeline, degradation signals, and output consistency.

---

## Phase 1: Canonical Engine Output Shape
The engine exposes two primary analysis entry points with differing schemas, which is a major source of contract drift.

### 1. `PreflightEngine` + `ReportBuilder` (Core Orchestrator)
This is the intended industrial output.
```json
{
  "ok": true,
  "timestamp": "ISO-8601",
  "summary": {
    "risk_level": "LOW|MEDIUM|HIGH|CRITICAL",
    "risk_score": 0-100,
    "issue_count": 0,
    "critical_count": 0
  },
  "document": {
    "name": "string",
    "size": 0,
    "page_count": 0,
    "pdf_version": "unknown"
  },
  "issues": [
    { "id": "string", "severity": "string", "message": "string", "page": 0, "fixable": false }
  ],
  "engines": { "preflight_engine": "v1.9.0-deterministic", "signature": "hex" }
}
```

### 2. `AnalyzeCommand` (CLI/Worker Wrapper)
```json
{
  "ok": true,
  "status": "SUCCESS",
  "findings": [],
  "wrapper_metadata": { "request_id": "string", "timestamp": "...", "pages": 0, "size_bytes": 0 }
}
```

**Mandatory Keys:** `ok`, `timestamp`, `summary`, `document`, `issues`.
**Missing Keys:** `analysis`, `forensics`. These are currently downstream interpretations not generated by the kernel.

---

## Phase 2: Large / Complex PDF Behavior
1. **Timeout Guardrails**: `Ghostscript.js` enforces a **30s timeout**. Large PDFs (like the 19.6MB case) are likely to trigger this if they require deep rendering or technical probes.
2. **Silent Failure Mode**: `PreflightEngine.js` catches analyzer failures (including timeouts) and silently continues. It returns a "Success" (`ok: true`) payload with **zero findings**, which directly leads to the `dataMissing: true` state in the UI.
3. **Mock Dependency**: `PdfTechnicalEngine.analyze` currently returns a **hardcoded mock geometry** (210x297mm). For complex PDFs that require real technical extraction, this prevents any real analysis from occurring, effectively returning "no issues" for all files.

---

## Phase 3: Degradation Signals
**Status: MISSING.**
- There are no `partial`, `degraded`, or `incomplete` flags in any current output shape.
- The engine marks an analysis as `ok: true` even if all technical modules fail, as long as no fatal risk was *successfully detected*.

## Phase 4: Field-Name Consistency Matrix

| Concept | PreflightEngine Shape | AnalyzeCommand Shape | CLI Adapter Shape | Recommended Canonical |
| :--- | :--- | :--- | :--- | :--- |
| **Issue List** | `issues` | `findings` | `engine_result.findings` | `issues` |
| **Metadata** | `document` | `wrapper_metadata` | `wrapper_metadata` | `document` |
| **Status** | `ok` (bool) | `status` (string) | `engine_result.status` | `ok` + `status` |
| **Forensics** | N/A | N/A | N/A | `forensics` (To be added) |

---

## Phase 5: Upstream Compatibility Gaps
1. **Worker Contract**: The worker likely expects `analysis` or `forensics` keys. Since the engine doesn't emit them, they are being lost or nullified in the persistence layer.
2. **UI Interpretation**: The UI sees `issues: []` and a mock-default `document` size of `0`, triggering the "Analysis data unavailable" warning.

---

## Phase 6: Engine Contribution & Verdict

### Does the engine contribute to the bug?
**YES.**
- It converts technical failures (timeouts/errors) into silent "Successful but Empty" reports.
- It provides no metadata indicating that the analysis was partial or degraded.
- It uses a mock `TechnicalEngine` that masks real PDF structure.

### Final Verdict
The engine contributes via **degraded-success semantics** and **missing degradation flags**. While the worker/BFF also have mapping issues, the engine is generating "Deceptive Success" payloads for large files.
